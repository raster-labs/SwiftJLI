# Headless Swift 6.4 validation

`validate.sh` invokes the Python 3 standard-library runner. Run it from any directory; it finds this repository from its own location. It selects Xcode through `DEVELOPER_DIR` and never changes `xcode-select`. Contract 0.5.0 relaxed the single pinned preview-Xcode build to an accepted range: **Swift 6.2 or 6.4** passes, and the exact toolchain is recorded as evidence rather than enforced as an admission gate. Xcode is recorded when present but is not required, since Linux gates and a swift.org toolchain have no `xcodebuild`. Any other Swift version fails before build qualification.

```sh
DEVELOPER_DIR=/Applications/Xcode.app/Contents/Developer ./Scripts/validate.sh
```

The default run checks debug and release clean/incremental builds and tests, a fresh standalone local consumer, five fixed repetitions of selected ownership/cancellation tests, and build-associated SPDX/CycloneDX SBOM generation. It requests **`--build-system swiftbuild`** by default, overridable with `--build-engine`.

Four capabilities are probed rather than assumed, because contract 0.5.0 keeps **Swift 6.2** an accepted toolchain and 6.2 supplies none of them. Where one is missing the run records an unexecuted gate under POL-08, prints it at the end and continues, rather than failing on an accepted toolchain:

| Capability | Absent on | Behaviour |
| --- | --- | --- |
| `swift build --sbom-spec` | Swift 6.2 | SBOM generation skipped; `sbom_supported: false` |
| `swift test --maximum-repetitions` | Swift 6.2 | Repetitions run as that many separate executions instead, each validated and logged |
| Swift Build engine, name collision | a case-insensitive filesystem **and** manifest names differing only in case | Falls back to the native engine. Not triggered since the 23 September rename |
| Swift Build engine, test enumeration | Swift 6.2 | `swift test list` returns the build log and no test identifiers, so every gate below would have nothing to run. Falls back to the native engine; `build_engine` records what ran |

The engine fallback is a naming guard, not a toolchain limit. Swift Build names each product's intermediates directory after the product, so a product whose name differs from a target's only in case shares that directory on a case-insensitive filesystem — the macOS default — and the two overwrite each other's dependency files, failing with "unable to open dependencies file". That is why the executable is `swiftjli-cli` and not `swiftjli`: the latter collided with the `SwiftJLI` module and made Swift Build unusable on macOS. The check remains because it is cheap and states the invariant the name now satisfies; it no longer fires here, and `requested_build_engine` and `build_engine` are both in the report. Each run gets a new evidence directory and isolated build/cache paths. Build concurrency defaults to two workers per command; use `--jobs` (1–32) deliberately when running several repositories in parallel.

```sh
# Add separate AddressSanitizer and ThreadSanitizer builds/runs.
./Scripts/validate.sh --sanitizers

# Select a bounded subset; this does not qualify omitted checks.
./Scripts/validate.sh --checks debug,repetition --repetitions 10

# In a host sandbox that refuses SwiftPM's nested sandbox only:
./Scripts/validate.sh --disable-package-sandbox --output /absolute/new/evidence-directory
```

`--disable-package-sandbox` is an explicit workaround for `sandbox-exec: sandbox_apply: Operation not permitted`; it disables only the nested SwiftPM sandbox. It does not weaken concurrency, compiler safety checks or the outer host sandbox. Leave it off on an ordinary supported runner.

`report.json` records exact argument arrays, command exit codes, logs, source hashes, toolchain identity, selected/omitted checks, discovery and execution counts, and open gates. A command failure, timeout, zero discovered/selected/executed tests, a discovered/executed declaration mismatch, or a skipped test ends the run unsuccessfully. The script retains all failure evidence. It never uses `--repeat-until pass` or retries a failing test until green.

Swift Testing's xUnit output counts test declarations, including a parameterised test as one declaration. The report separately counts passing argument cases and their fixed repetitions from the raw test log; logs remain authoritative. The runner enables XCTest too if it discovers XCTest imports/subclasses in the source, so it cannot silently hide new XCTest cases. A sandbox bundle-loading failure is a failed environment gate, not zero passing XCTest tests.

SBOMs are generated by `swift build --product <this-package> --sbom-spec spdx|cyclonedx`, using the exact candidate graph and build invocation. Their SHA-256 values are recorded. If the installed tool reports missing validation schemas, that warning becomes an explicit open gate; JSON parsing alone is not schema validation. The separate `swift package generate-sbom` command is graph-only and must not be substituted as build-associated evidence. SwiftPM's SBOM does not inventory every toolchain/platform or non-SwiftPM component.

This script covers local macOS validation of the existing Milestone 1 API/storage surface. It does not claim real codec operation, native Linux/Intel or device execution, Swift 6.2 comparison, fresh URL consumer resolution, Xcode GUI/front-end qualification, performance measurements, or release approval. Those remain separate evidence. The CLI help and supported values are captured in every successful run; no unverified hosted CI image is assumed.

## CLI checks

Active packages and generated consumers require Apple OS 26.0. The owner-approved CLI foundation is a separate executable product, with no main entry point in library tests. After building its release binary, run `python3 Scripts/test-cli.py --binary /absolute/path/to/the/tool --output /new/evidence/directory` for process-level help/verbosity/stream and staged install/man-page checks. The check requires `man` and `mandoc`; missing manual tools fail explicitly. `install-cli.sh --help` describes install/update and DESTDIR staging. Read [CLI.md](../CLI.md) and the [OS 27/CLI record](../Documentation/Engineering/OS27CLI/README.md), whose CLI content is current and whose platform claims are superseded history.

## Independent JPEG interoperability

Use libjpeg-turbo 3.2.0 development tools (`cjpeg` and `djpeg`) for these
repeatable public-API checks. Each command needs a fresh evidence directory;
no oracle process is used by the shipping library.

```sh
python3 Scripts/verify-lossless-interop.py --output-dir /new/lossless-evidence --scratch-path /new/oracle-build
python3 Scripts/verify-dct-interop.py --output-dir /new/dct-evidence --scratch-path /new/oracle-build
python3 Scripts/verify-raw-rgb-interop.py --output-dir /new/raw-rgb-evidence --scratch-path /new/oracle-build
```

The raw RGB extension uses independently encoded 8/12-bit sequential/progressive
files, both scalar and automatic backends, and allocating/padded caller storage.
It checks 16 decode/storage combinations, allocation identity and untouched
prefix/row padding. The existing DCT maximum-error limits remain 2 sample units
for 8-bit and 4 for 12-bit; the check does not infer a lower-precision or colour
conversion. Commands, tool output and generated-fixture hashes are retained.

## Shared-storage suite integration

[SuitePairIntegration](../Examples/SuitePairIntegration/README.md) extends the
original two-codec harness to all twelve directions among the four implemented
codecs. `verify-suite-outputs.py` checks the 72 completed outputs with independent
JPEG/JPEG 2000/JPEG-LS/JPEG XL decoders. `verify-cross-codec-heap.py --suite`
requires 72 allocator cases and 72 deliberate-copy controls; omitting `--suite`
retains the original two-codec checks. These are development-only tools.
